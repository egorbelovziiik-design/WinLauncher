# KINGGRIEF — «Твоя империя грифа»

Донат-платформа и магазин для Minecraft-сервера: витрина привилегий, кейсов, риликов и услуг, корзина с промокодами, оплата ЮKassa/Robokassa (плюс тестовый режим), автоматическая выдача через плагин-мост и полноценная админ-панель.

Проект написан с нуля: дизайн, тексты, структура и код собственные, без копирования чужих магазинов. Палитра — тёмный «имперский» фиолетовый неон с золотом, шрифты Unbounded + Manrope (self-hosted, кириллица).

---

## Живая демонстрация

- Сайт: **https://kinggrief.vercel.app**
- Админка: **https://kinggrief.vercel.app/admin** (`admin` / `KingGrief-2026`)

Демо развёрнуто на Vercel из ветки `arena/32c6aa2e-winlauncher` (подкаталог `kinggrief`, проект `kinggrief`).
Платёжный провайдер в демо — `mock`, поэтому на странице заказа доступна кнопка тестовой оплаты, реальные деньги не списываются.

> Ограничение демо: на Vercel файловая система доступна только для чтения, поэтому SQLite живёт в `/tmp` (`DATABASE_PATH=/tmp/kinggrief.db`).
> Каждый экземпляр функции создаёт свою базу: витрина и админка полностью работоспособны (админская сессия не зависит от базы), но заказы, правки каталога и **аккаунты игроков** могут не сохраняться между холодными стартами и не разделяются между инстансами.
> Для продакшена используйте Docker с постоянным томом (см. ниже) или подключите PostgreSQL.

## Что внутри

**Витрина**

- Главная страница с баннером, живым онлайном, избранными привилегиями и последними покупками.
- 14 привилегий (PEGAS … D.OWNER) — с индивидуальным цветом, иконкой, описанием, перками, кнопками «Купить» и «Подробнее», свечением при наведении. У D.OWNER — 3D-корона на CSS-вокселях, радужная анимированная рамка, золотые частицы и бейдж «МАКСИМАЛЬНЫЙ РАНГ».
- Страница сравнения привилегий: таблица перков, которая целиком редактируется из админки.
- 3 группы кейсов (СУПЕР, ЛЕГЕНДАРНЫЙ, МЕГА) по 3 набора; страницы кейсов с наградами и **реальными** шансами из базы. У каждой награды есть описание, привилегии ведут на свою страницу и собраны в отдельный блок «Привилегии из этого кейса», демо-анимация открытия показывает описание выпавшего предмета.
- Рилики: 9 пакетов от 1 000 до 100 000, калькулятор с серверным пересчётом цены по редактируемой формуле.
- Услуги: разбан / размут / разбан по IP / размут по IP с формой никнейма.
- **Аккаунты игроков**: регистрация, вход по нику или email, личный кабинет с историей заказов, смена почты и пароля. Заказы связываются с аккаунтом, никнейм и email подставляются в оформление.
- Корзина: количество, промокоды, сохранение после перезагрузки, анимации добавления, пересчёт на сервере.
- Оформление заказа, страница статуса заказа, повторная проверка платежа.
- Отзывы с модерацией, правила, поддержка, профиль игрока по никнейму.
- Тёмный дизайн, mobile-first, `prefers-reduced-motion`, скелетоны загрузки, кастомные 404 и 500.

**Админ-панель `/admin`** — 11 разделов: дашборд, заказы, товары, кейсы, промокоды, покупатели, аналитика, отзывы, дизайн, настройки, безопасность. Плюс журнал действий, CSV-экспорт, 2FA (TOTP), роли.

**Интеграции** — ЮKassa, Robokassa, тестовый провайдер `mock`, плагин-мост для Paper/Purpur/Spigot через LuckPerms и любые консольные команды из редактируемого шаблона.

## Быстрый старт

Требуется **Node.js 22+** (нужен встроенный модуль `node:sqlite`).

```bash
cd kinggrief
npm install
cp .env.example .env          # заполните секреты
npm run dev                   # http://localhost:3000
```

Первый запрос создаёт базу, каталог, настройки, промокоды и администратора из `.env`.

Продакшн:

```bash
npm run build
npm start                      # http://0.0.0.0:3000
PORT=8080 npm start            # другой порт
BIND_HOST=127.0.0.1 npm start  # только localhost
```

`npm start` запускает standalone-сборку (скрипт `scripts/start.mjs` копирует статику и поднимает сервер Next.js), поэтому предупреждений `next start` не возникает.

Обязательный минимум в `.env`:

```env
ADMIN_SESSION_SECRET=<openssl rand -hex 32>
ADMIN_PASSWORD=<ваш пароль>
MINECRAFT_BRIDGE_SECRET=<openssl rand -hex 24>
```

Полный список — в `.env.example`.

## Аккаунты игроков

Помимо покупки «гостем», на сайте есть полноценные аккаунты:

| Страница | Что делает |
| --- | --- |
| `/register` | Никнейм (3–16 символов, латиница/цифры/`_`), email, пароль (от 8 символов, буква + цифра), согласие с правилами |
| `/login` | Вход по никнейму **или** email; `?next=` возвращает туда, откуда пришёл |
| `/account` | История заказов со статусами, сумма покупок, смена email и пароля, выход |

Что важно знать:

- Пароли хранятся как `scrypt`-хэш, сессия — httpOnly cookie со сроком 30 дней.
- Никнейм и email уникальны (регистр не важен): `Steve` и `steve` — один аккаунт.
- Покупки привязываются к аккаунту (`orders.user_id`), поэтому заказ виден в кабинете и в админке.
- Гость может оформить заказ без регистрации — аккаунт не обязателен.
- Список зарегистрированных аккаунтов виден администратору в разделе «Покупатели».

## Оплата

Три провайдера, выбор через `PAYMENT_PROVIDER` или в админке.

**`mock` (по умолчанию).** Заказ создаётся со ссылкой `/checkout/<номер>?demo=1`, оплата подтверждается кнопкой в тестовом режиме (`POST /api/payments/mock/confirm`). Такие заказы помечаются демо и исключены из реальной аналитики. В боевом режиме эндпоинт отвечает 403.

**ЮKassa.** Создание платежа через `/v3/payments` с `Idempotence-Key = order.id`, редирект на `confirmation_url`. Вебхук `POST /api/payments/webhook/yookassa`:

1. принимает уведомление,
2. **не доверяет телу запроса** — повторно запрашивает платёж в API ЮKassa по `payment_id`,
3. сверяет `paid/status`, сумму в копейках и `metadata.orderId`,
4. идемпотентно помечает заказ оплаченным и ставит выдачу в очередь.

Настройка: укажите URL `https://<домен>/api/payments/webhook/yookassa` в личном кабинете, включите события `payment.succeeded` и `payment.canceled`.

**Robokassa.** Платёж формируется с подписью MD5 (`login:OutSum:InvId:Password1`). `ResultURL` — `POST /api/payments/webhook/robokassa`; проверяется подпись `OutSum:InvId:Password2`, сумма и номер заказа (`InvId`), ответ — `OK<InvId>` для подтверждения. `SuccessURL`/`FailURL` ведут на страницу заказа.

Общее для всех реальных провайдеров:

- сумма и состав заказа перепроверяются на сервере, оплата «чужой» суммы отклоняется;
- повторное уведомление не создаёт дубликат выдачи (проверка статуса заказа + уникальный индекс задач выдачи);
- каждая попытка пишется в таблицу `payments` (сырое тело уведомления сохраняется);
- действия администратора логируются в `audit_log`.

> **Важно:** реальные списания ЮKassa/Robokassa в этом окружении **не проверялись** — нет боевых ключей и доступа к платёжным шлюзам. Проверены тестовый провайдер, подписи, проверка сумм и идемпотентность. Перед приёмом денег сделайте тестовую покупку у провайдера в его песочнице.

## Выдача в Minecraft

Схема: магазин → очередь выдачи в БД → плагин опрашивает сервер → выполняет команды от консоли → подтверждает выполнение.

```
POST /api/minecraft/poll   (заголовок x-bridge-secret)
  → { "commands": [{ "id", "command", "nickname", "orderId" }], "interval": 5 }

POST /api/minecraft/ack    (заголовок x-bridge-secret)
  ← { "results": [{ "id": "…", "ok": true }] }
```

Плагин: `minecraft-plugin/` (Paper/Purpur/Spigot 1.20.6, Java 17). Установка:

1. Соберите jar: `cd minecraft-plugin && mvn package` (нужен доступ к `repo.papermc.io`).
2. Скопируйте `target/KingGriefBridge-1.0.0.jar` в `plugins/`.
3. В `plugins/KingGriefBridge/config.yml` укажите `api-url` (адрес сайта) и `secret` (тот же, что `MINECRAFT_BRIDGE_SECRET`).
4. Перезапустите сервер.

Команды выдачи редактируются в админке («Настройки» → «Команды выдачи») как JSON-шаблон с плейсхолдерами `{player}`, `{rank}`, `{amount}`, `{case}`, `{order}`, `{product}`. Плагин принимает только команды из белого списка префиксов (`lp`, `crates`, `relics`, `money`, `give` … — настраивается).

Если в одном заказе несколько привилегий, они выдаются командой `parent set` (шаблон `rank_replace`) в порядке возрастания цены — в итоге у игрока остаётся старшая группа, а не набор из всех.

Защита от двойной выдачи: задача выдачи создаётся один раз на позицию заказа, вебхук идемпотентен, статусы `pending → sent → delivered`, ошибки сохраняются с текстом и доступны для ручного повтора в админке.

> **Jar не собран** в этом окружении: сборка требует доступа к репозиторию PaperMC и Maven. В репозитории лежат полные исходники, `pom.xml`, `plugin.yml` и инструкция.

## Docker

```bash
cp .env.example .env      # задайте ADMIN_SESSION_SECRET, пароль, секрет моста
docker compose up -d --build
docker compose logs -f app
```

- Образ: multi-stage, Next.js `output: standalone`, работает от непривилегированного пользователя.
- Данные: именованный том `kinggrief-data` → `/app/data` (файлы SQLite).
- Healthcheck: `GET /api/status`.
- Порт хоста меняется через `APP_PORT`.
- За TLS-прокси поставьте `COOKIE_SECURE=true`.

Остановка: `docker compose down`. Полное удаление данных: `docker compose down -v` (удалит том с базой).

## Тесты

```bash

npm run test:e2e    # e2e против запущенного сервера (нужен npm run dev / npm start)
```

**Юнит-тесты** (`tests/kinggrief.test.ts`, 36 проверок): фиксированные цены 14 привилегий, состав каталога, сумма шансов кейсов = 100 %, интерполяция калькулятора риликов, промокоды (процент, лимит, минимальная сумма, категории, исчерпание), серверный расчёт корзины, создание заказа, отклонение неверной суммы, идемпотентность подтверждения оплаты, задачи выдачи и закрытие заказа, scrypt-хэши, TOTP, аудит, модерация отзывов, исключение демо-заказов из аналитики.

**E2E** (`scripts/e2e.mjs`, 76 проверок по HTTP): все публичные страницы и 404, редирект и закрытость админки, вход (в т.ч. отказ при неверном пароле), 11 страниц админки, CSRF (без токена — 403, с токеном — 200), серверные цены и отказ некорректной корзине, создание заказа → тестовая оплата → очередь выдачи → ack → статус «выдан», проверка секрета моста, `/api/status`, экспорт CSV с BOM, выход из сессии.

Покрытие e2e: страницы, админка, CSRF, корзина и цены, оплата и выдача, мост Minecraft, аккаунты игроков, cookie-флаги, CSV.

Контейнерный прогон:


## Безопасность

- **Пароли:** scrypt (Node `crypto`), сравнение `timingSafeEqual`.
- **Сессии:** httpOnly cookie с HMAC-подписанным токеном (12 часов у админа, 30 дней у игрока). Токен проверяется без обращения к базе, поэтому вход работает и на serverless, где нет общего файла БД; в middleware проверяется подпись и срок, чтобы не было мигания закрытых страниц.
- **Cookie в iframe/превью:** при HTTPS ставится `SameSite=None; Secure; Partitioned` (CHIPS — иначе браузер не сохранит сессию в стороннем iframe), на локальном HTTP — `SameSite=Lax`. Именно из-за этого раньше вход в админку «срабатывал», но следующая страница снова показывала форму.
- **Проверка входа:** после успешного логина форма запрашивает `/api/admin/session` (и `/api/auth/me` для игрока) и, если браузер всё-таки не сохранил cookie, показывает кнопку «открыть в новой вкладке» вместо тихого возврата на экран входа.
- **CSRF:** отдельный токен в cookie + заголовок, привязанный к сессии; проверка `Origin` для мутаций.
- **RBAC:** роль администратора (`owner` / `admin` / `manager`) в модели и проверках `requireRole`.
- **Валидация:** Zod на всех входах, серверный пересчёт цен, ограничение длины и типов.
- **Rate limiting:** вход, оформление заказа, промокоды, публичные API.
- **Заголовки:** `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, `poweredByHeader: false`.
- **XSS:** React-экранирование, запрет `dangerouslySetInnerHTML` для пользовательских данных.
- **Аудит:** вход, изменения настроек/товаров, демо-операции, ручные выдачи и ошибки.
- **2FA:** TOTP (RFC 6238, SHA-1, 6 цифр, окно ±1 шаг).
- **Секреты:** только через переменные окружения; `.env` в `.gitignore`.
- **Выдача:** только после подтверждённой оплаты, идемпотентно, с журналом ошибок.

## Что проверено, а что нет

Проверено в этом окружении (Node 22, локальный запуск, без Docker и без боевых ключей):

- `npm install`, `npm run lint` (tsc), `npm run build`, `npm test` (36/36), `npm run test:e2e` (76/76).
- Все публичные страницы и 11 страниц админки отвечают 200; админка закрыта без сессии.
- Сквозной сценарий: корзина → заказ → тестовая оплата → очередь выдачи → ack → статус «выдан» → аналитика.
- CSRF (403 без токена / 200 с токеном), rate limit, 401 на админском API, CSV-экспорт UTF-8 с BOM.
- Аккаунты: регистрация → сессия → заказ в кабинете → выход → вход по email → смена профиля; повторная регистрация ника и слабый пароль отклоняются.
- Cookie админской сессии: HttpOnly, на HTTP без `Secure`, на HTTPS с `Secure; SameSite=None`; редиректы работают за reverse-proxy.
- Шансы кейсов, промокоды, серверный пересчёт цен, идемпотентность оплаты — покрыты тестами.

**Не проверено:**

- Реальные платежи ЮKassa и Robokassa: нет боевых ключей и доступа к шлюзам. Код интеграции, подписи и проверка сумм реализованы, но требуют тестового платежа в песочнице провайдера до приёма денег.
- Сборка и запуск плагина на живом Minecraft-сервере: jar не собирался (нет доступа к `repo.papermc.io`), протестирован только серверный протокол моста.
- Нагрузочное тестирование и работа под большим трафиком.
- Docker-образ не собирался в этом окружении (Docker недоступен); файлы `Dockerfile` и compose-файлы подготовлены и соответствуют структуре проекта.

## Эксплуатация и развитие

**Резервные копии.** `npm run db:backup` создаёт консистентный снимок через `VACUUM INTO` в `backups/`. Для Docker: `docker compose exec app node -e "…"` или копирование тома. Рекомендуется ежедневный cron + выгрузка за пределы сервера.

**Сброс базы.** `npm run db:reset` (спросит подтверждение; `-- --yes` для CI). Каталог и администратор создадутся заново при первом запросе.

**Переход на PostgreSQL.** Замените реализацию в `src/lib/db.ts`/`repo.ts` на Prisma-клиент с той же схемой (`products`, `cases`, `case_items`, `orders`, `payments`, `deliveries`, `promos`, `promo_uses`, `reviews`, `admin_users`, `sessions`, `audit_log`). Остальной код зависит только от функций репозитория.

**Масштабирование.** Приложение stateless относительно файловой системы, кроме SQLite; для нескольких реплик нужна внешняя БД. Мост Minecraft рассчитан на несколько серверов: каждый опрашивает общую очередь, выдача привязана к заказу и подтверждается.

**Чего сознательно нет.** Выдуманных цифр онлайна, отзывов и статистики: на пустой базе показываются честные нули и пустые состояния, а онлайны берутся из последнего ответа плагина (`/api/status`). Пока мост не подключён, блок статуса прямо пишет «мост Minecraft не подключён». Демо-заказы создаются только вручную и всегда помечены `is_demo`.

**Замените плейсхолдеры.** IP `play.kinggrief.net`, Discord/Telegram, версия сервера, баннер, объявление и контакты поддержки заданы как пример и меняются в разделах «Дизайн» и «Настройки».
