# KingGriefCore 6.6.4 — исправление зависания при поиске ивентов

На показанном логе зависание произошло в старом синхронном поиске места
ивента: основной поток ждал `World.getChunkAt(...).load()`. Замена только
этого JAR не удаляет миры, данные игроков, конфиг и другие плагины.

## Установка на работающий сервер через файловую панель

1. **Остановите сервер полностью** и дождитесь статуса «остановлен». Сделайте
   резервную копию мира, данных игроков, папки `plugins` и конфигурации вне
   папки сервера или скачайте её на компьютер.
2. Откройте папку `plugins/`. Найдите старые JAR-файлы KingGriefCore, в том
   числе файлы с именами вроде `KingGriefCore (16).jar`. Переместите их в
   резервную копию **за пределами `plugins/`**. Имена могут отличаться: имя
   плагина внутри JAR указано как `name: KingGriefCore` в `plugin.yml` или
   `paper-plugin.yml`. Не перемещайте JAR других плагинов.
3. Проверьте `plugins/update/`, если она есть. Отложенные JAR-обновления
   KingGriefCore также вынесите в резервную копию: сервер может применить их
   при запуске и подменить свежий JAR.
4. Скопируйте прилагаемый `KingGriefCore.jar` в `plugins/`. Там должен быть
   **ровно один** JAR с именем плагина `KingGriefCore`. Не удаляйте и не
   заменяйте папку данных `plugins/KingGriefCore/`, миры или другие плагины.
   Не распаковывайте всю сборку поверх существующего мира ради этого патча.
5. Запустите сервер обычным полным запуском, **не `/reload`**. В консоли
   выполните `version KingGriefCore` (в игре — `/version KingGriefCore`):
   должна отображаться версия **6.6.4**. В начале `logs/latest.log` ищите
   строку `[KingGriefCore] [Install] Active KingGriefCore v6.6.4; JAR=...;
   SHA-256=...`. SHA-256 прилагаемого JAR:

   `910eb3afb8d6f772f89bb1dbb0b345d73cedbabbcbf9349bab2cb421b41e8890`

   Имя JAR в журнале может отличаться, если вы его переименовали. Если при
   старте видите `[Install] Other KingGriefCore JARs`, остановите сервер и
   вынесите перечисленные старые файлы из `plugins/`. Если Core вообще не
   включился из-за дубликатов, такая проверка не успеет выполниться: смотрите
   ранние ошибки Paper и проверьте файлы вручную. Никакие файлы диагностика
   автоматически не удаляет и не изменяет.

## Настройки на случай нехватки ресурсов

По умолчанию автоматические ивенты включены, а новые чанки при необходимости
запрашиваются у Paper асинхронно, по одному. Сначала Core ищет безопасную
площадку в уже загруженных чанках. Ожидание ограничено; при тайм-ауте поиск
прерывается, удержанные чанки освобождаются, а отмена запроса выполняется по
возможности (Paper может продолжить уже запущенную работу).

Если серверу тяжело, можно **не обязательно** добавить в существующий
`plugins/KingGriefCore/config.yml` блок ниже, не удаляя остальные настройки.
При наличии блока `events:` измените его, не создавайте второй блок с тем же
именем. После изменения полностью перезапустите сервер:

```yaml
events:
  auto-enabled: true
  allow-chunk-generation: false
  min-free-heap-mb: 256
```

`allow-chunk-generation: false` не создаёт новые чанки для ивентов. Если среди
уже загруженных нет подходящего безопасного участка, ивент не появится — это
нормальное безопасное поведение. Для возврата обычного режима задайте `true`.
`auto-enabled: false` выключает только автоматический запуск; ручной запуск
для администраторов остаётся доступным, но соблюдает те же ограничения поиска.

`min-free-heap-mb` — минимальный запас внутри **Java heap** перед запросом новых
чанков, по умолчанию 256 МиБ. Это не свободная память всего контейнера и не
гарантия от OOM. При недостатке heap новый запрос откладывается; уже
загруженные площадки по-прежнему могут использоваться.

На скриншоте панель показывает около 4.16 ГиБ при лимите 4 ГиБ. Это отдельный
риск нехватки памяти, но само по себе не доказывает причину зависания. Для
Paper 1.21.4 рекомендуется Java 21. При лимите контейнера 4 ГиБ оставьте запас
для нативной памяти JVM и других процессов: например, начните с максимума Java
heap около 3 ГиБ и проверьте потребление после запуска. Если хостинг сам задаёт
`-Xmx`, меняйте лимит в его настройках, не добавляя второй конфликтующий
флаг. Реально необходимый объём зависит от мира, плагинов и игроков; при
нехватке ресурсов уменьшите нагрузку или увеличьте лимит сервера.

Если проблема повторится **после полной замены и перезапуска**, сохраните
`logs/latest.log` и пришлите новый стек watchdog целиком, строку `[Install]`,
результат `version KingGriefCore`, версию Paper/Java и показатель RAM. В журнале
могут быть IP и другие персональные данные — перед отправкой при необходимости
скройте их.
